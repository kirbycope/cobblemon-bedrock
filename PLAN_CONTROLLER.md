# Cobblemon Bedrock: controller support for the custom screens

Written for the agent executing this. Read `PLAN.md`'s "Ground rules" first; they all apply (everything under
`development_*_packs/` is generated by `port.py`, never hand-edited; verify in the client; short steps; commit
nothing unless asked). The watchdog rule in `C:\GitHub\CLAUDE.md` applies to `port.py --fix` and `tools/deploy.py`.

## The report

Planet Minecraft, comment 10875587 on the Cobblemon Bedrock listing, by CosmicReaper575, 2026-10-07:

> Is this controller compatible cause i tried to select a starter and nothing was working. If it isn't are
> planning to make it controller compatible.

Kirbycope's reply so far: "I didn't even think to test that since Java doesn't have it either." Nothing else on
the listing's comments is about input. The listing's "How It Works" says the starter screen opens on first
join, so a controller player is stuck at the very first thing the add-on shows them.

## What the starter screen is

`openStarter()` in `scripts/main.js` (about line 6758) sends an `ActionFormData` titled `cbm:starter` with
thirteen buttons: nine starter slots (three categories of three), `choose`, `exit`, and the two page arrows.
`ui/server_form.json` hides the vanilla long form whenever the title begins `cbm:` and draws the port's own
layout instead; the starter layout comes from `create_starter_ui()` in `port.py` (about line 7135). Every one
of the port's screens works the same way. The titles in `main.js` are: `cbm:starter`, `cbm:summary`, `cbm:pc`,
`cbm:pasture`, `cbm:pokedex`, `cbm:interact`, `cbm:dialogue`, `cbm:tm`, `cbm:pot`, `cbm:trade`,
`cbm:challenge`, `cbm:battle_menu`, `cbm:battle_moves`, `cbm:battle_switch`.

## Diagnosis (a hypothesis until step 1 reproduces it)

Every button the port generates is a raw control:

```json
{"type": "button", "collection_index": n,
 "default_control": "default", "hover_control": "hover", "pressed_control": "pressed",
 "button_mappings": [{"from_button_id": "button.menu_select", "to_button_id": "button.form_button_click", "mapping_type": "pressed"},
                     {"from_button_id": "button.menu_ok", "to_button_id": "button.form_button_click", "mapping_type": "focused"}],
 "bindings": [{"binding_type": "collection_details", "binding_collection_name": "form_buttons"}]}
```

The vanilla long form's buttons are `common_buttons.light_text_button`, which chains to `common.button` in
Mojang's `ui_common.json`, and that template is what makes a button reachable without a pointer:

```json
"button": {"type": "button", "focus_enabled": true, "focus_magnet_enabled": true, "focus_wrap_enabled": true,
           "default_focus_precedence": 0, "focus_identifier": "", "focus_change_down": "", ...}
```

The port's buttons set none of the `focus_*` properties. A control that is not focus-enabled cannot be reached
by the D-pad or the stick, and the `button.menu_ok` mapping only fires on the focused control, so with a
controller nothing on any `cbm:` screen can be selected or pressed. Mouse and touch go through
`button.menu_select` with `mapping_type: pressed`, which needs no focus, which is why it was never noticed.
Keyboard arrow keys use the same focus system, so they should fail the same way; that is a cheap way to
reproduce before any controller is involved.

The eleven places in `port.py` that build such a button (line numbers as of today): 6368, 6803, 7062, 7210,
7295, 7569, 7827, 7997, 8186, 8308, 8467. The `grid` battle menus use the one at 8467 through their
`grid_item_template`, so they are covered by the same fix.

## Steps

### 1. Reproduce before changing anything

The PC has an Xbox Wireless Controller paired over Bluetooth (`Get-PnpDevice` shows it OK) and nothing to
fake one: no ViGEmBus driver, no `vgamepad`. So:

- Keyboard first, scripted: deploy as is, join, `/scriptevent cobblemon:starter reset` from chat, then
  `client_drive.key("up")`, `down`, `left`, `right`, `enter`, with a `shot` after each. Expect no slot to
  highlight and `enter` to do nothing. A `shot` of the vanilla form (any non-`cbm:` form, for example the
  evolution prompt, or a `/scriptevent` that opens one) with the same keys shows the contrast.
- Controller, by hand: ask Kirbycope to try the paired Xbox controller on the same screen and say what
  happens. If they prefer an automated controller test, ask before installing anything: ViGEmBus is a kernel
  driver (admin install from the nefarius/ViGEmBus releases page) and `pip install vgamepad` drives it; that
  would add `pad <button>` and `pad hold <button> <seconds>` commands to `tools/client_drive.py`. The client
  switches to controller mode on its own the moment it sees gamepad input. Do not install the driver without
  the go-ahead.

### 2. Fix in `port.py`, not in the JSON

Add one helper near the first button builder and use it from all eleven, so the properties live in one
place (KISS; the current eleven copies of the same `button_mappings` are what let this slip):

```python
FORM_BUTTON = {"type": "button", "focus_enabled": True, "focus_magnet_enabled": True, "focus_wrap_enabled": True,
               "default_control": "default", "hover_control": "hover", "pressed_control": "pressed",
               "button_mappings": [{"from_button_id": "button.menu_select", "to_button_id": "button.form_button_click", "mapping_type": "pressed"},
                                   {"from_button_id": "button.menu_ok", "to_button_id": "button.form_button_click", "mapping_type": "focused"}],
               "bindings": [{"binding_type": "collection_details", "binding_collection_name": "form_buttons"}]}
```

Each builder spreads `**FORM_BUTTON` and adds its own `size`, `offset`, `collection_index`, `layer` and
`controls`. Keep the hover control as the focus visual: Bedrock draws `hover_control` for the focused button,
and every screen already has a `_hover` texture, so no new art is needed.

Only if step 3 shows focus landing nowhere, or wandering into the hidden vanilla form, add in this order and
re-test after each: `default_focus_precedence: 1` on the control that should start focused on each screen
(the starter's first slot; a screen's first menu entry; the battle menu's Fight); `focus_container: true` on
each `cobblemon_*` panel; `focus_navigation_mode_<dir>: "contained"` only where wrapping leaves a screen.
Hidden controls (`#visible` false, which is how empty starter slots and absent party tiles are hidden) are not
focusable, so they need nothing.

Regenerate with `python port.py --fix` (about 90 seconds, under the watchdog), then `python tools/deploy.py`
(about 60 seconds; bumps the version the client caches by). Never run only part of the generator (see
`PLAN.md`, the invisible-blocks note).

### 3. Verify in the client

Same keys as step 1, now expecting the slot to highlight and `enter` to pick. Then walk every `cbm:` screen
with the arrow keys and `enter` once each; the testing commands in `README.md` open them without playing up to
them (`cobblemon:starter reset`, `cobblemon:summary`, `cobblemon:wheel`, `cobblemon:trade_test`,
`cobblemon:battle`, the PC and healing machine by using them, a Poke Mart clerk for `cbm:dialogue`). The
battle screens need a real battle; check Fight, the move grid, Switch and Back.

Then the controller, by hand or with the virtual pad: D-pad and left stick move focus, A selects, B closes
(`button.menu_cancel` maps to exit on the screen already). Also confirm, with the controller, the in-world
controls the listing documents still work, since they are all vanilla inputs: Party item use, sneak twice to
reopen the starter screen, sneak and use a Pokemon for its wheel, hold use for the scanner, the ride controls
and the ride overlay's `:_input_key.*:` hints, which should show controller glyphs. Send before and after
screenshots of the starter screen with `SendUserFile`, and one of each other screen with its focus highlight.

Both logs stay clean: no new `[error]` lines in `C:\GitHub\bedrock-server\bds.out.log` or the newest
`%APPDATA%\Minecraft Bedrock\logs\ContentLog*.txt`.

### 4. Documentation

- `README.md`: in the client-driving section, the new `pad` commands if they were added; under the controls, a
  sentence that every screen can be driven by controller, keyboard arrows or touch.
- `docs/planetminecraft.html` ("Good to Know"): one line saying controllers are supported since this version,
  so the listing's next edit carries it.
- If anything stays unsupported on controller, say exactly what in both places rather than leaving it out.

### 5. Release and reply

`python tools/build_addon.py`, then the `gh release create v<version>` line from the README, with notes naming
the controller fix. Hand Kirbycope a draft reply for the thread, something like: "Fixed in <version>: the
screens were only clickable, not focusable, so a controller could not reach them. Download the new .mcaddon
from the release." Kirbycope posts it and updates the listing; do not post anywhere yourself.

## Out of scope

Rebinding, new keybinds, or a controller layout of the HUD. Bedrock add-ons cannot add keybinds (the listing
already says so), and the HUD (`hud_screen.json`) has no buttons.

## Outcome (2026-10-08)

Done on the PC with a virtual controller (ViGEmBus and vgamepad; `tools/client_drive.py padhost` and `pad`).

- **Reproduced first.** On 1.0.336 the D-pad moved nothing and A did nothing on the starter screen.
- **Focus.** `FORM_BUTTON` in `port.py` gives every generated button focus; all eleven builders use it.
- **Invisible buttons.** Turning focus on made the transparent placeholder buttons focusable too, so focus could
  land on nothing. `FOCUS_BINDINGS` turns focus off for any button whose texture names `none`, and `scripts/main.js`
  passes `HIT` (`textures/ui/cobblemon/hit`) for the transparent buttons that do act: the dialogue box, the search
  fields, the Summary's stat sub-tabs, marks and ride centre, the pot's recipe overlay and your own trade slots.
  `hit_hover` and the PC's `bar_hover` are a faint white wash, the only focus sign a transparent button can show.
- **Hover frames.** The Pokedex page arrows (also the starter's) and the cry button had a hover identical to their
  normal frame; `focus_frame()` makes one.
- **Found on the way, not controller related.** The battle Switch tiles and the TM machine's party slots asked for
  `party/bNN`, which became `bNNc`/`bNNo` with the Party in Poke Balls change, so they drew the missing texture.
- **Out of memory.** `render_portraits.render_all` opened one worker per core (24), about 900 MB each; it now
  caps at eight.
- **Verified with the controller:** starter (pick, page arrows, I choose you!, B closes), interact wheel, Summary
  (tabs, markings, stat sub-tabs), PC, Pokedex, battle (Fight, moves, Switch, Back, Forfeit), trade screen,
  TM machine, campfire pot, NPC dialogue. **Not verified:** the battle and trade request screen between two real
  players.
- **Known rough edges.** A form opens with no focus shown until the first D-pad press, and a screen that reopens
  after a pick (the starter, the PC) starts focus over. Server forms cannot keep focus across a reopen.
